# 阶段 1 计划：图纸工具 MVP（PC 网页 + 微信小程序）

> 版本 v0.2 · 2026-10-30 · 状态：**已确认**（2026-10-30 用户选择：Vue 网页 + uni-app 小程序、共享核心；先网页后小程序）
> 范围变化：2026-10-30 用户要求「小程序和 PC 网页端也要做」。原方案的阶段 1 只做小程序（H5 顺带编译），现改为两端都要做成可用的产品。

## 1. 范围

两端的功能相同，都对应方案第 3 节的模块 1~5（本地部分）：

| 模块 | 内容 | 说明 |
|---|---|---|
| 1 图片转图纸 | 上传、裁剪、风格（卡通 / 照片 / 像素图）、尺寸档（省豆 48 / 均衡 72 / 细节 100 + 自定义 10~200）、最大颜色数、品牌 + 色数档、去背景开关、生成 | 算法直接用 `@pd/pattern-core`，在 Worker 里跑 |
| 2 品牌色卡 | 品牌、色数档选择；色卡浏览（色号 + 色块） | 数据来自 `@pd/palettes`；色数档仍是算法生成的占位数据 |
| 3 图纸编辑器 | 移动、画笔、橡皮、取色、油漆桶、替换整色、撤销 / 重做、水平镜像 | 只改格子，不改原图 |
| 4 导出 | 带色号的大图（PNG）、用量清单、镜像图；PC 下载文件，小程序存相册 | 导出内容两端一致 |
| 5 本地作品 | 自动保存草稿、作品列表、继续编辑、删除 | 只存本机：PC 用 IndexedDB，小程序用本地文件；云端同步在阶段 2 |

**不做**：登录、云端、分享口令、文字 / 二维码转图纸、品牌互转、豆豆、后台（都在后续阶段）。

## 2. 技术路线（2026-10-30 已确认：推荐方案）

### 2.1 推荐：两个外壳 + 共享核心

```
packages/pattern-core   算法（已完成）
packages/palettes       色卡（已完成）
packages/editor-core    新增：图纸文档、编辑命令、撤销重做、用量统计、草稿序列化
packages/render         新增：图纸渲染与导出排版（只依赖标准 Canvas 2D 接口，两端共用）
apps/web                新增：PC 网页（Vue 3 + Vite + TS），同时适配手机浏览器
apps/miniapp            新增：微信小程序（uni-app Vue 3 + TS，只编译微信小程序）
```

- **共享的部分**：算法、编辑逻辑、渲染和导出排版全部写成与平台无关的 TS 包。两端只写界面外壳和平台适配（选图、Worker、存储、保存文件）。
- **为什么 PC 网页不用 uni-app 的 H5 输出**：uni-app 的 H5 本质是手机页面，放到电脑上是一条窄长页面。PC 端需要的大画布、右侧参数面板、鼠标滚轮缩放、快捷键（Ctrl+Z 等）、拖拽上传、直接下载文件，用普通 Vue 网页做更直接，也不用到处写条件编译。
- **代价**：界面要写两套（估计多 30% 左右的界面工作量），但逻辑只写一份。

### 2.2 备选：uni-app 一套代码

小程序和 H5 都用 uni-app 编译，H5 用宽屏适配（leftWindow / rightWindow）做 PC 布局。界面工作量最少，但 PC 体验受限，Canvas、Worker、文件 API 要写条件编译，调试也要依赖 uni-app 工具链。

## 3. 实施顺序（推荐先网页、后小程序）

| 子阶段 | 内容 | 验收 | 粗估 |
|---|---|---|---|
| **1a 共享核心 + PC 网页** | ① 先修阶段 0 遗留的 5 个问题（见第 6 节）；② editor-core、render 两个包 + 单测；③ apps/web 全流程 | Chrome / Edge / Safari 桌面和手机浏览器（390 宽）都能跑通：上传 → 裁剪 → 生成 → 编辑 → 导出 PNG；刷新后草稿不丢；100×100 生成 < 1 秒（桌面） | 6~8 天 |
| **1b 微信小程序** | apps/miniapp：同样流程；`wx.createWorker` 跑算法；Canvas 2D 渲染；导出存相册 | 微信开发者工具 + 真机（iOS、Android 各一台）跑通全流程；100×100 生成 < 3 秒（中端机）；主包 ≤ 2MB | 5~7 天 |

先做网页的理由：
- 浏览器里改完立刻能看，编辑器、导出这些最复杂的部分能最快打磨好；
- 不依赖小程序 AppID、开发者工具和真机，你随时可以打开试用；
- 1b 时小程序只需要做外壳，核心逻辑已经被网页验证过。

**小程序需要你准备**：小程序 AppID（开发阶段可用测试号）；真机测试需要一台 iOS、一台 Android。上线前还需要 ICP 备案（阶段 1 不上线）。

**PC 网页的部署**：阶段 1 只在本地运行（`pnpm dev`）和打包成静态文件，不对外发布。国内服务器上线需要域名 + ICP 备案，放到阶段 2 和后端一起处理。

## 5. 关键设计

- **Worker**：网页用 Web Worker，小程序用 `wx.createWorker`；两边都把 `pattern-core` 打包成单文件、转成 ES2015。生成时界面显示「正在生成…」，可取消。
- **撤销重做**：每次笔划记录被改动格子的「旧值 / 新值」，内存占用与改动量成正比，不随图纸大小增长；上限 200 步。
- **草稿格式**：图纸（格子数组 + 色板 + 参数 + 原图缩略图）存成 JSON，格子数组压缩存储；带版本号，便于阶段 2 上传云端。
- **重新生成会覆盖手工修改**：有手工修改时先确认，并自动留一个恢复点。
- **大图导出**：200×200 格、每格 24px 时导出图约 4800px 见方，小程序端需分块绘制，避免超出 Canvas 尺寸上限（1b 真机实测）。

## 6. 开工前要先修的阶段 0 遗留问题

来自 `docs/阶段0-算法报告.md` 第 8.10 条，接入 Worker 前修掉：

1. 去背景时主体整段贴边（如半身像肩膀横贯底边）会被当成背景删除；
2. 1 行或 1 列的网格被当成环形边框，结果全部被删；
3. 纯色块图片在像素图预设下被误判为像素周期；
4. 全空结果（全透明图、全部被去背景删掉）需要返回明确的状态，界面给提示；
5. 确认 Worker 打包会把 `??`、`?.` 等语法转成 ES2015。

另外 3 条要在阶段 1 的界面和实现里处理：

6. 高级设置里提供「细线保护」开关：照片上它偶尔会把五官阴影加深，用户要能关掉（报告第 8 节第 13 条）；
7. 漫漫品牌 S4 一码两色：用量表里会出现两条同色号、不同色值的记录，界面要合并显示或给出提示（报告第 8.10 条）；
8. 两端在调用算法前先把原图缩到长边 ≤ 2048：4000×3000 原图直接输入时，细笔画检测在 Node 上约 1 秒、内存约 100MB（报告第 8 节第 13 条）；
9. v0.5 加入细笔画检测后耗时上升，开启去背景时还会再翻倍：1b 真机实测 100×100 / 291 色 + 去背景的耗时，超过 3 秒就降级（例如去背景时关闭第二遍，或预览先用 Oklab）。
