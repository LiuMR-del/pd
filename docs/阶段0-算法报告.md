# 阶段 0 算法报告

> 日期 2026-10-29 · 对应方案 v0.4 · 数据来源：`pnpm bench` 生成的 `tools/bench/out/results.json`（生成于 2026-10-29T10:51Z，Node v24.16.0，Apple M5；10:51 这次只比 10:34 多了 k=1 评审组，其余数据除耗时的正常波动外一致）
> 复现：仓库根目录执行 `pnpm install && pnpm bench`，打开 `tools/bench/out/index.html` 可逐图对比。

## 1. 结论速览

| 问题 | 结论 |
|---|---|
| 色差公式 Oklab 还是 CIEDE2000 | **CIEDE2000，配合 Oklab 预筛 K=8 个候选**（`metric: 'ciede2000', prefilterK: 8`）。用中立指标 CAM16-UCS 评判，它在 8 类 × 2 预设共 16 组对比中全部优于或等于 Oklab，速度比精确 CIEDE2000 快约 1.5 倍。Oklab 留作低端机降级选项。理由见第 4 节 |
| 我们的管线 vs perler-beads 原版 | 原版默认参数会把整张图合并到只剩约 3 种颜色（原因见 3.1），CAM16 色差是我们的约 2 倍。关闭原版的合并后，与我们相比：色差接近，但用色是我们的 2.6~4.5 倍，孤立单颗约是我们的 35 倍，几乎没法拼 |
| 性能 | 100×100 网格、MARD 72 色：推荐配置 41~80ms；全 291 色时 82~165ms。远低于 1s 的目标 |
| 去背景 | 合成图上主体误删率为 0%（原版：渐变底 89%、主体触边 16%）；背景残留 ≤ 1.4% |
| 竞品 | 5 张图、72 格、24 色。CAM16 平均：豆格 7.37，今天拼豆了吗（本地复刻、近似）7.73；我们用同一 221 色板时 6.20~6.47，用 291 色时 5.85~6.07。孤立单颗：我们 0.3~0.4%，两家 2.3~3.7%。**两家的暗线召回和细字清晰度都比我们好（82~83% 对 75~81%）**，这是我们要追的短板 |
| 像素图 | 整数倍放大的像素图能精确对齐（周期 6、零误差还原）；YouTube 缩略图这类非整数缩放的像素图检测不到周期，自动退回普通网格（已知问题） |

## 2. 实现范围

- `packages/pattern-core`：纯 TS、零运行时依赖。`tsconfig` 的 `lib` 只开 ES2020、不含 DOM，编译期就能拦住 DOM 和 Canvas 用法。
  - 色彩转换：sRGB / 线性 / XYZ / Lab / Oklab。
  - CIEDE2000：Sharma 2005 的 34 组测试数据全部通过，误差 < 5e-5。
  - 可插拔距离：`oklab` / `ciede2000`，后者可加 Oklab 预筛。
  - 色板预计算：按色板签名缓存；最近色查询用亮度下界剪枝，并按量化后的查询色缓存。
  - 线性光空间区域平均重采样、宽高比网格、整数像素周期检测。
  - 单格 k×k 投票，含中心加权和暗线保护。
  - 限色：Ward 式加权贪心合并、显著色保护，外加一轮限定在色板内的 k-means 精修。
  - Lab 误差扩散抖动。
  - 后处理：孤立点、小色块、去背景、裁边。
  - 预设：3 种风格 × 3 档尺寸。
  - baseline：perler-beads 原版管线。
  - 编辑工具：perler-beads 编辑函数移植。
- `packages/palettes`：perler-beads 的 291 色 × 5 品牌色卡，转换成我们的 JSON 结构，配校验脚本和单测。
- `tools/bench`：程序生成的合成图、指标、预览图、总览图、静态对比页，以及参数扫描、性能测试、预筛一致率测试。

## 3. 评测方法

- **测试集**：22 张真实图（7 类，CC BY，见 `tools/bench/images/manifest.csv`），外加 9 张程序生成的合成图：色块、渐变、细线、点阵字、白底主体、渐变底主体、主体触边、原生像素图、6 倍放大像素图。其中 4 张带真值掩码（另有 1 张像素图同时带掩码）。
- **主矩阵**：色板 MARD 全 291 色；均衡档（长边 72 格，上限 24 色）；卡通 / 照片两种预设。

| 组别 | 说明 |
|---|---|
| baseline | perler-beads 原版：卡通 = dominant，照片 = average，相似色阈值 30（原版默认） |
| baseline-nomerge | 同上，但关闭相似色合并（公平对照） |
| ours-oklab | 我们的管线 + Oklab |
| ours-ciede2000 | 我们的管线 + 精确 CIEDE2000 |
| ours-ciede2000-k8 | 我们的管线 + CIEDE2000 + Oklab 预筛 8 个候选（推荐默认） |

- **指标**：参考值 = 原图在同一网格上做线性光区域平均的结果。

| 指标 | 含义 |
|---|---|
| ΔE00 | 每颗豆与参考格的 CIEDE2000 色差均值。**天然偏向 CIEDE2000 组** |
| ΔEok | Oklab 欧氏距离 ×100 的均值。**天然偏向 Oklab 组** |
| ΔE CAM16 | CAM16-UCS 色差均值。与两种匹配公式都无关，作为两组之间的**中立裁判** |
| 平滑 ΔE00 | 图纸与参考都做 3×3 平滑后再比，抖动结果「整体对就行」时可以得分 |
| 用色数 | 图纸实际用到的颜色数 |
| 孤立单颗 | 8 邻域内没有同色豆的格子占比 |
| 暗线召回 | 含暗线的格子（其子采样最暗 L* < 25）中，被画成深色（L* < 35）的比例 |
| 主体误删 / 背景残留 | 只在带掩码的合成图上计算 |
| 耗时 | 生成一张图纸的毫秒数 |

- **指标局限**：参考值是「格内平均色」，所以凡是追求边缘干净、不出现混合色的手段（投票、暗线保护），ΔE 都会变差。这类改动要结合暗线召回和对比页来判断。

### 3.1 关于 baseline 只用约 3 种颜色

perler-beads 在 2026-04-08 的提交 `ba83fbd`（「使用LAB空间距离」）中，把颜色距离从 RGB 欧氏距离（0~441）改成 Oklab×100（黑白距离为 100），但默认合并阈值仍是 30。新量纲下 30 相当于全量程的 30%，所以 commit `2efee730` 的默认参数会把大部分颜色合并掉。我们的 baseline 是对它的忠实移植，并有单测验证。为了公平，另设了 baseline-nomerge 组。

### 4.6 Oklab 预筛 K 个候选与精确 CIEDE2000 的一致率

查询集：22 张真实图按 216 列做线性平均后的全部像素，共 692,928 个颜色。

| 色板 | K | 结果一致率 | 平均 ΔE00 损失 | 最大损失 | 耗时（精确 → 预筛） |
|---|---|---|---|---|---|
| 72 | 4 | 90.97% | 0.344 | 17.09 | 1031 → 467ms |
| 72 | **8** | **98.11%** | **0.032** | 6.80 | 1031 → 697ms |
| 72 | 16 | 99.93% | 0.0004 | 2.10 | 1031 → 1195ms |
| 291 | 4 | 87.82% | 0.177 | 10.88 | 2654 → 1092ms |
| 291 | **8** | **95.01%** | **0.063** | 5.91 | 2654 → 1458ms |
| 291 | 16 | 98.65% | 0.012 | 3.90 | 2654 → 2097ms |

K=8 时，按 ΔE00 计的平均损失可以忽略，而按 CAM16 计整体反而略好（照片 6.45 对 6.52，卡通 6.88 对 6.98）。原因是预筛排除了「CIEDE2000 认为近、但 Oklab 认为远」的候选，抑制了 CIEDE2000 在大色差下偏饱和的选色。

#### 4.7.2 今天拼豆了吗（本地复刻，近似）

**为什么是复刻**：注册需要手机号，用户不愿使用。经用户授权（2026-10-30），只下载了 pindoule.cn 公开加载的前端 JS 分包，不登录、不调用接口，下载的代码只读、不执行。按照它的转换逻辑，用 TypeScript 写了一个复刻版。

**复刻版放在仓库外**：`~/Downloads/tool/PD-local/pindoule/`，含规格说明 `SPEC.md`（每一步都注明了原代码行号）、`replica/replica.ts`、`run-bench.ts`。竞品代码不进入本仓库，原因有两个：
- 本仓库按 AGPL 开源，放进来等于公开它的代码；
- 违反 8.4 隔离原则。

复刻版的输出（网格 JSON）放在 `tools/bench/competitors/*__pindoule-replica.json`，该目录不入库。

**复刻出的默认管线**（网页端，「混合」算法 + 卡通模式，72 格、24 色）：
1. 长边缩到 1024 以内。
2. 自动裁掉近白或透明的边缘，四周各留「长边 / 72」的余量。
3. 5×5 保边平滑。
4. 每格只取**中心 1 个像素**。
5. 从四边洪泛近白格作为背景。
6. CIEDE2000 匹配，色板为 MARD 221 色。
7. 限色三步，24 色对应 balanced 档：
   - ΔE76 ≤ 7.5 的相近色两两合并，直到剩 20 色；
   - 少于 12 格的稀有色，并入 ΔE ≤ 18 以内的最近色；
   - 最后强制合并到 24 色。
8. 主体外的格子和背景都写成 H02 白豆。
9. 生成后一定执行一次近色孤岛降噪：同色块最多 4 格，邻域支撑 ≥ 4，ΔE76 ≤ 28（强支撑时放宽到 42），共 3 轮，带肤色保护。

**与真实输出的差异**（结果只能视为近似）：
- 浏览器的高质量缩放，用 sRGB 空间区域平均来近似；
- 没有模拟上传页可能做的白底重绘和 JPEG 压缩；
- 「柔和」算法和小程序端分支没有复刻。

| 我们 推荐配置（同 221 色板）/ 照片 | 5.45 | 4.53 | 6.20 | 16.0 | 0.43% | 74.6% |
| 我们 推荐配置（291 色）/ 照片 | **5.19** | **4.36** | **5.85** | 16.6 | 0.32% | 79.0% |

**结论**
- 两家竞品都用 221 色。我们换成同一色板后，CAM16 仍比两家低 12~20%，孤立单颗约为它们的 1/8。
- 色板从 221 换成 291，又带来约 6% 的提升。在合成主体图上，221 色里没有足够亮的橙色，这一张图上两边差距最大（3.19 对 2.27）。
- 两家的暗线召回都高于我们：今天拼豆了吗只取中心像素，豆格也不做区域平均，所以细线和细字更「硬」。
- 复刻版会把主体自动裁到撑满网格，比如 text_01 变成 72×49、白底主体变成 72×65。主体因此获得更多格数，这是一个值得借鉴的产品设计。

#### 4.7.3 色卡数据发现

复刻代码证实，今天拼豆了吗的 MARD 色值与 perler-beads 同源，只有 R11 不同（它是 `#FFEBFA`）。差异主要出在豆格。
豆格图纸上显示的 59 种颜色里，只有 16 种与 perler-beads 的 MARD 色值完全一致。读取豆格用色表上的色号确认，属于「同一色号、色值不同」：

## 6. 最终推荐：CIEDE2000（+ Oklab 预筛 K=8）

1. **中立指标支持 CIEDE2000**：CAM16-UCS 与两种匹配公式都无关。按它评判，在 8 类 × 2 预设共 16 组对比中，推荐配置全部优于或等于 Oklab（差距最小的是合成图 4.30 对 4.33、AI 图照片预设 8.64 对 8.68）。全体平均比 Oklab 低约 3.5%（卡通 6.88 对 7.14，照片 6.45 对 6.68）。精确 CIEDE2000 与推荐配置之间互有高低，差距 ≤ 0.25。
2. **视觉上可以接受**：精确 CIEDE2000 在深蓝、天空等大色差处会选更饱和的颜色（第 4.6 节），加 Oklab 预筛后这种倾向减轻，CAM16 也更好。
3. **性能足够**：推荐配置在 100×100 / 72 色时为 41~80ms，耗时是精确 CIEDE2000 的约 0.6~0.85 倍、Oklab 的约 3 倍，桌面端远低于 1s。
4. **Oklab 的定位**：最快（约 20ms），CAM16 只比推荐配置差约 3.5%。保留为「低端机 / 实时预览」的降级选项：拖动滑杆时用 Oklab 出预览，松手后用推荐配置出最终图纸。

## 8. 已知问题与待人工评审

1. **k=1（纯平均）与 k=3（投票）的取舍需要看图决定**：现有指标以「格内平均色」为参考，天然偏向平均。k=1 的 ΔE 明显更低，但暗线召回差 16 个百分点，边缘会出现大量过渡色。对比页里已加入 `ours-ciede2000-k8-k1 / cartoon` 列（全部图平均：CAM16 5.44 对 6.88，孤立单颗 0.14% 对 0.22%，暗线召回 73.1% 对 89.0%）。请对照 `ours-ciede2000-k8 / cartoon` 列，重点看卡通类和文字类的边缘观感。
2. **深色底上的浅色细笔画**：卡通预设下，深色背景（L* ≈ 18，接近暗线阈值 luma 45 对应的 L* 17.6）上约 1 格宽的浅色笔画，仍可能被暗线保护吞掉。已加入「邻域以浅色为主」和「必须紧贴浅色格」两道判断，有所改善但没有根除。临时办法：这类图用照片预设，或把 luma 调到 35（扫描显示暗线召回 88.4%、ΔE 更低）。
3. **真实像素图检测不到周期**：只支持整数倍放大。非整数缩放或经过 JPEG 压缩的像素图会退回普通网格。后续可以加小数周期搜索，或让用户手动指定格数。
4. **1px 细线丢失**：网格较粗时（每格约 9px），覆盖比例低于 30% 的线达不到暗线保护阈值。这是物理分辨率的限制，可以通过提高网格或降低 ratio 缓解。
5. **去背景规则依据不足**：「边缘连续段」规则是被合成图问题驱动加入的，真实去背景样本不足（只有 portrait_02 一张纯色底人像，没有掩码），需要补充带掩码的真实样本。
6. **色卡数据问题**（来自 perler-beads 原始数据，未修改）：
   - 漫漫 `S4` 同时对应 `#7FCD9D`（MARD R18）和 `#F3C1C0`（MARD R24），已记入 `knownIssues`，按色号反查时取第一个。
   - CSV 里盼盼 P06 / P07 / P08 的备选色号 70 / 68 / 67，同时是 R09 / R08 / R01 的主色号，反查有歧义，校验脚本会给出警告。
   - 除 MARD 外，其他品牌都是按 MARD 色值映射的，**不是实测色值**。
7. **色数档是算法生成的占位数据**：24 / 48 / 72 / 96 / 120 / 144 / 168 / 221 色档，由 CIEDE2000 最远点采样（从最接近白和黑的颜色起步）生成，标记为 `synthetic: true`，**不是官方套装清单**。拿到官方清单后替换 `scripts/build.ts` 中的生成逻辑即可。
8. **今天拼豆了吗只有复刻近似结果**（见第 4.7.2 节）。如果以后能拿到它的真实导出图，按 `<图片id>__pindoule.png` 放入 `competitors/` 就能验证复刻版的准确度；前提是它的导出版式和豆格类似，否则需要调整提取器。
9. **性能只测了桌面 Node**：小程序 Worker 真机耗时需在阶段 1 实测，按第 4.5 节估计。
10. **提交前代码审查发现的问题（2026-10-29，不阻断提交，阶段 1 接入 Worker 前须修）**：
    - **去背景遇到主体整段贴边**：比如半身像，蓝色肩膀横贯整个底边，占边框格子 ≥ 20% 且是一整段，会被当成背景整片删除。1 行或 1 列的网格会被当作环形边框处理，结果全部被删。默认不开去背景，所以不影响默认出图。需要用带掩码的真实人像样本重新设计种子规则。
    - **像素周期误判**：纯色块 logo（例如大面积单色方块）会被误判为像素图周期，用户选的长边被忽略。只在像素图预设下触发。
    - **全空结果没有提示**：全透明图，或整张图都被去背景删掉时，返回 0×0 的结果，前端需要提示用户。
    - **漫漫 S4 一码两色**：选漫漫品牌时，结果里会出现两条色号相同、色值不同的记录，前端需要处理。
    - **ES2020 语法**：`??`、`?.` 等写法要确认 uni-app 打包 Worker 时会转成 ES2015。
    - **已修复**：
      - 参数校验：cols/rows 限制在 1~200 且必须成对给出；longSide、subSamples 等拒绝 NaN；pixelPeriod 必须 ≥ 1。
      - 计时改用 `typeof performance` 判断，不再依赖 `globalThis`。
      - 暗线投票为空时回退到均值匹配。
      - 删除一处死代码，修正匹配缓存「近似」的注释。
11. **细小文字可读性和暗线召回不如两家竞品**（第 4.7 节）。初步判断：我们的投票、平坦区取均值、孤立点清理会把 1 格宽的深色笔画弱化或抹掉；豆格对文字和描线更「硬」。可以考虑的方向：文字和描线区域检测、按局部对比度放宽暗线阈值、提高 protectContrast。需要阶段 1 前后专门做一轮实验。
12. **MARD 色值表来源不一致**（第 4.7 节）：perler-beads 和豆格对同一色号给出的色值不同，59 种颜色里只有 16 种完全一致。在拿到官方色卡或实物测色之前，图纸颜色的「真实度」无法最终确定。这会影响所有色差结论的绝对值，但不影响各组之间的相对比较。
